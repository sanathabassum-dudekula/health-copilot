## The problem

Prescriptions, laboratory reports, discharge summaries, and other health documents often live in separate places. This makes it difficult to see what happened over time or prepare a clear overview for a healthcare visit.

**CuraMind is being developed to help people organise medical documents, review information extracted from them, and build a clearer health history.**

The goal is to make health information easier to navigate—not to replace a clinician or make medical decisions.

## What we're building

- **One place for health records** — bring supported medical documents and health information into a more organised experience.
- **Document understanding** — extract medicine names, dosages, lab/test values, diagnoses, and dates where those details are present.
- **Human review first** — keep extracted information out of the health record until a person checks it; allow correction/removal of common lab, medicine, diagnosis, and allergy fields, or rejection of the extraction.
- **Plain-language summaries** — summarise reviewed information while making uncertainty clear.
- **Multilingual health assistant** — chat with profile-aware health information in English, Hindi, Telugu, or Tamil; use an in-page voice/text panel with visible page context, attach temporary scans, and discuss uploaded medical reports before reviewing them for the health record.
- **Health insights and reminders** — review recorded out-of-range results and comparable trends; get optional, general routine suggestions for meals, sleep, and wellbeing; use confirmed prescription details when creating medicine reminders.
- **Private profile chooser** — after sign-in, see the profiles connected to your account and open separate health records for each. Existing linked-profile records are preserved.
- **Wearable vitals** — connect compatible Bluetooth Low Energy devices that expose standard Heart Rate, Pulse Oximeter, or Health Thermometer services; enter readings manually when Bluetooth is unavailable. Saved readings appear in the health overview and timeline, and can be shared with Lumi for cautious review.
- **A unified health timeline** — organise reports, diagnoses, medicines, and dated vital readings by date when reliable dates are available.
- **Broader health history** — structured injury/fracture extraction and limited women's-health document extraction are present; longitudinal workflows and extra privacy controls remain incomplete.
- **Existing baseline preservation** — retain existing download/export behaviour while the project evolves.

> **Important:** These are the product goals. See [Project status](#project-status) for what is present in the repository and what still needs end-to-end verification.

### Stage 1: the end-to-end health-record workflow

Stage 1 is considered complete only when this entire flow works and has been tested:

1. Upload a supported medical document.
2. Extract medicines, dosages, test values, diagnoses, and dates.
3. Show extracted details beside the original for review, correction/removal where supported, explicit confirmation, or rejection.
4. Create a summary from reviewed information.
5. Display confirmed information in a unified health timeline.

A file picker or individual screen alone does not complete Stage 1. Update this README's status only after the complete workflow has passed end-to-end tests using synthetic sample documents.

## Remaining release priorities

1. **Before real patient data:** complete an independent security/privacy review, verify authentication and authorization across all family-profile routes, and establish production backups, retention, and incident-response procedures.
2. **Before clinical claims:** evaluate extraction and summaries against a reviewed synthetic test set that includes scans and handwriting; keep clinician review in the loop and do not treat AI output as diagnosis.
3. **Before production operation:** configure and test persistent production database/file storage, migrations, monitoring, and recovery. The current local test suite does not establish production readiness.
4. **External integrations:** live ABDM/ABHA and verified doctor registries and consent-managed consultations require provider registration and credentials. Background reminder delivery requires Web Push credentials and a GitHub Actions scheduler.
5. **Further review coverage:** add field-level correction for injury and women's-health extraction, plus a fuller audit history for changes and family-profile decisions.

## Run locally

These commands are for local development on Windows PowerShell. Open **separate terminal windows** for the frontend and backend. Use synthetic test documents only.

### Prerequisites

- Git
- Node.js and npm
- Python compatible with `backend/requirements.txt`
- A configured model-provider API key only if you intend to test an LLM-backed extraction path
- Additional system tools only if required by the enabled OCR/document-processing path

### 1. Clone the repository

```powershell
git clone https://github.com/sanathabassum-dudekula/health-copilot.git
Set-Location .\health-copilot
```

### 2. Configure and start the backend

In a new PowerShell terminal:

```powershell
Set-Location ".\backend"
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Open `backend\.env` locally and configure the model/provider settings and S3-compatible storage settings required for document uploads. Keep real keys in `.env`; never commit that file.

Start the API:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

If the backend reports a missing setting, database dependency, or external service, check `backend/app/config.py`, `backend/app/db.py`, and the current README/configuration before changing the database. **Do not delete or recreate an existing database to troubleshoot startup.**

### 3. Configure and start the frontend

In a second PowerShell terminal:

```powershell
Set-Location "C:\path\to\health-copilot\frontend"
npm ci
Copy-Item .env.example .env.local
npm run dev
```

Open the URL printed by Next.js. This workspace has used `http://localhost:5173`; use the actual URL printed by the dev server if it differs.

**Check the API proxy before testing API-dependent pages.** Locally, both the backend command and frontend default use `http://127.0.0.1:8000`. On Vercel, the frontend defaults to the deployed backend at `https://curamind-backend.vercel.app`; `BACKEND_URL` can override that at build time. Keep local overrides in `.env.local` rather than hard-coding deployment secrets.

### 4. Run backend tests

From the repository root:

```powershell
Set-Location ".\backend"
.\.venv\Scripts\python.exe -m pytest
```

If the repository has a `requirements-dev.txt` file and pytest is not installed, install those development dependencies first. Do not assume that file exists; check the `backend` directory.

### 5. Build the frontend

In a separate terminal:

```powershell
Set-Location "C:\path\to\health-copilot\frontend"
npm ci
npm run build
```

A successful build is useful, but it does not prove the full medical-document workflow, access control, or production deployment is safe.

## Deployment overview

**The web frontend and FastAPI backend are separate Vercel projects connected to this GitHub repository.** Configure each project's root directory to match its application folder. The current project domains are `https://health-copilot-eight.vercel.app` and `https://curamind-backend.vercel.app`.

### Frontend on Vercel

1. Connect the GitHub repository and set **Root Directory** to `frontend`.
2. Use the detected Next.js framework and `npm run build`.
3. Set `BACKEND_URL` to `https://curamind-backend.vercel.app` for Production. The fallback in `frontend/next.config.ts` uses that URL on Vercel and `http://127.0.0.1:8000` locally.
4. Redeploy after changing environment variables and verify `/api/openapi.json` and an authenticated or guest API flow.

### FastAPI backend on Vercel

1. Connect the same GitHub repository and set **Root Directory** to `backend`. `backend/index.py` exports `app.main:app`, and `backend/requirements.txt` declares the Python runtime dependencies.
2. Attach a persistent Neon PostgreSQL database. The application accepts `DATABASE_URL` or the Vercel Neon integration's `DATABASE_URL_UNPOOLED`; the local SQLite default is for development only.
3. Add `LLM_API_KEY` in the backend Vercel project's Production environment to enable document extraction, summaries, and AI assistant features. Store the key only in Vercel environment settings, never in Git.
4. Configure the S3-compatible storage variables in Vercel for persistent uploaded files. Do not rely on the function's local filesystem for uploads.
5. For background reminders, add `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, and a random `CRON_SECRET` to the backend Production environment. Add the same `CRON_SECRET` as a GitHub Actions repository secret. Generate a VAPID key pair with a trusted local Web Push key generator; never commit or paste the private key into GitHub or chat. Use the app's HTTPS URL for `VAPID_SUBJECT`. The `Reminder Push Dispatcher` workflow calls the protected backend dispatcher every five minutes; GitHub may delay scheduled workflow starts. Redeploy after setting the backend variables, and enable Actions for the repository.
6. After deployment, verify the backend OpenAPI route and the frontend `/api/` proxy; check Vercel Runtime Logs if either returns a server error. Enable background reminders from the Reminders page in each browser/device that should receive them.

The hosted prototype has working frontend/API connectivity, but a successful deployment is not a production-readiness or clinical-safety certification. Before real health information is used, independently verify access controls, storage configuration, database backups/recovery, retention, monitoring, and privacy/security safeguards. Test uploads, document processing, review, summaries, timeline, downloads, and permissions with synthetic data.

## Privacy, safety, and limitations

Medical records are sensitive. This project is under development and should not be treated as a production medical-record service.

- Never commit `.env` files, API keys, access tokens, private certificates, or real patient records.
- Use synthetic or properly de-identified test documents.
- Treat extracted information as unconfirmed until reviewed.
- Do not invent missing values or dates; communicate uncertainty.
- Do not present generated summaries as diagnoses or treatment plans.
- Require appropriate authentication, authorisation, and explicit consent before sharing records.
- Give pregnancy, fertility, and other women's-health information additional privacy protection.
- Complete a security and privacy review before allowing real users to upload sensitive health information.

## Disclaimer

CuraMind is a software prototype intended to help organise and review health information. It does not replace a qualified healthcare professional, provide emergency care, or independently diagnose conditions or prescribe treatment. Extracted data and generated summaries can be incomplete or incorrect. Medical decisions should be made with an appropriate healthcare professional.
